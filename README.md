## Overview

This project sets up a network-based intrusion detection system (NIDS) using
**Suricata**, configures custom detection rules, monitors traffic for
suspicious activity, and includes a lightweight Python tool that parses
Suricata's alert log, summarizes findings, visualizes them, and demonstrates
a basic automated response mechanism.

## Repository Contents

| File | Purpose |
|---|---|
| `local.rules` | Custom Suricata detection rules (recon, brute force, web attacks, C2/malware indicators, policy violations) |
| `alert_monitor.py` | Parses `eve.json`, live-tails new alerts, generates a severity/signature summary and chart, and auto-blocklists high-severity source IPs |
| `sample_eve.json` | Sample Suricata alert output for testing `alert_monitor.py` without a live sensor |
| `alert_summary.png` | Example chart output (generated by `--report`) |

## 1. Setting Up Suricata

Install on Ubuntu/Debian:

''bash
sudo apt update
sudo add-apt-repository ppa:oisf/suricata-stable -y
sudo apt install suricata -y
```

Verify the interface Suricata should monitor:

```bash
ip a
```

Set the monitored interface in `/etc/suricata/suricata.yaml`:

```yaml
af-packet:
  - interface: eth0   # replace with your interface
```

## 2. Adding the Custom Rules

Copy `local.rules` into the Suricata rules directory Suricata actually reads from (check `default-rule-path` in `suricata.yaml` — often `/var/lib/suricata/rules/`):

```bash
sudo cp local.rules /var/lib/suricata/rules/local.rules
```

Confirm it's referenced in `suricata.yaml`:

```yaml
rule-files:
  - suricata.rules
  - local.rules
```

Test the rule syntax and restart:

```bash
sudo suricata -T -c /etc/suricata/suricata.yaml -v
sudo systemctl restart suricata
```

## 3. What the Rules Detect

- **Reconnaissance**: Nmap SYN/null scans, ICMP ping sweeps
- **Brute force**: repeated SSH/FTP connection attempts, repeated HTTP 401s
- **Web attacks**: SQLi and XSS patterns in URIs, directory traversal, scanner user-agents (nikto, sqlmap, gobuster, etc.)
- **Malware/C2 indicators**: oversized DNS queries (tunneling), traffic to known backdoor ports, oversized ICMP payloads
- **Policy violations**: plaintext Telnet and FTP logins

Each rule uses a `threshold` clause where relevant to avoid single-packet
false positives and only fire on a pattern of repeated behavior.

## 4. Monitoring Traffic

Suricata logs alerts to `/var/log/suricata/eve.json` in JSON-lines format.
Live-tail alerts as they occur:

```bash
python3 alert_monitor.py --logfile /var/log/suricata/eve.json --follow
```

Generate a summary report and chart from existing logs:

```bash
python3 alert_monitor.py --logfile /var/log/suricata/eve.json --report
```

(`sample_eve.json` is included so this can be tested without a live sensor —
run `python3 alert_monitor.py --logfile sample_eve.json --report`.)

## 5. Response Mechanism

`alert_monitor.py` implements a basic automated response: any alert with
Suricata severity 1 or 2 (high/medium) has its source IP appended to
`blocklist.txt`, along with the equivalent `iptables` command to drop that
IP. In a production setup this could be wired directly into `iptables`,
`fail2ban`, or a firewall API call instead of just logging the command.

## 6. Testing the Setup

Generate traffic to trigger the rules in a lab environment (only against
systems you own or have authorization to test):

```bash
nmap -sS <target-ip>          # triggers the Nmap scan rule
hping3 -1 --flood <target-ip> # triggers the ICMP sweep rule
```

Confirm alerts appear in `eve.json` and in the `alert_monitor.py` output.

## 7. Visualization

Running `--report` produces `alert_summary.png`, a horizontal bar chart of
the top alert signatures by count — useful for a quick view of what kinds
of activity are being flagged most often.
